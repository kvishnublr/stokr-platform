# Execution Mode Verification Guide

This document outlines how to verify that PAPER, SIMULATION, and LIVE execution modes work correctly after signal generation.

## Overview

The stokr-platform implements three execution modes for trading:
- **PAPER**: Trades execute with simulated fills using market data (no real broker calls)
- **SIMULATION**: Same as PAPER mode (deterministic backtesting)
- **LIVE**: Trades execute against real broker APIs (gated by trader eligibility checks)

## Execution Flow Verification

### 1. Trigger Signal Generation (Replay)

Use the Admin API to replay a strategy and generate signals:

```bash
POST /api/admin/signals/replay
?strategyKey=NIFTY_50_BREAKOUT
&from=2026-05-01
&to=2026-05-10
```

Expected response:
```json
{
  "status": 200,
  "data": {
    "strategyKey": "NIFTY_50_BREAKOUT",
    "from": "2026-05-01",
    "to": "2026-05-10",
    "status": "STARTED",
    "message": "Replay running in background. Check Signal Monitor in ~60s."
  }
}
```

Wait 60 seconds for the replay to complete and generate signals.

### 2. View Generated Signals and Linked Orders

List all signals generated by the replay:

```bash
GET /api/admin/signals
?strategyName=NIFTY_50_BREAKOUT
&from=2026-05-01T00:00:00Z
&to=2026-05-10T23:59:59Z
```

Expected response shows signals with execution modes and order states.

### 3. Verify Signal Detail with Execution Timeline

## Verification Checklist

### ✅ PAPER Mode Verification

1. **Signal generates with ExecutionMode.PAPER**
   - Check the `executionMode` field in signal detail response
   - Should be `"PAPER"`

2. **Order created with correct execution mode**
   - Check linked orders in signal detail
   - `order.executionMode` should be `"PAPER"`

3. **Order executes without broker calls**
   - `order.state` should transition: `PENDING_SUBMISSION` → `ACCEPTED` → `FILLED`
   - `order.filledPrice` should be populated from market data
   - `order.brokerOrderId` should be NULL (not submitted to broker)

4. **Fill price based on market candles**
   - `filledPrice` should be within market candle prices (Open/High/Low/Close)
   - Slippage should be applied based on order size and volatility

### ✅ SIMULATION Mode Verification

1. **Signal generates with ExecutionMode.SIMULATED**
   - `signal.executionMode` should be `"SIMULATED"`

2. **Same execution flow as PAPER**
   - Order state transitions should match PAPER mode
   - Fills should be based on market data
   - No broker calls should occur

### ✅ LIVE Mode Verification

1. **Signal generates with ExecutionMode.LIVE**
   - `signal.executionMode` should be `"LIVE"`

2. **Order gated by trader eligibility**
   - If trader NOT eligible: `order.state` should be `REJECTED` or `FAILED`
   - Check rejection reason in order details (no broker credentials, eligibility check failed, etc.)

3. **Eligible traders execute against broker**
   - If trader IS eligible:
     - `order.state` should transition: `PENDING_SUBMISSION` → `ACCEPTED` → `FILLED`
     - `order.brokerOrderId` should be populated (real broker order ID)
     - `order.brokerVendor` should be set (e.g., "ZERODHA")

### ✅ Mode Isolation Verification

1. **PAPER trades don't hit broker API**
   - Check logs for absence of broker API calls for PAPER orders
   - `order.brokerOrderId` should be NULL for PAPER orders

2. **LIVE trades don't use simulated fills**
   - LIVE order fills come from broker, not from market data simulation
   - Check `order.brokerOrderId` is NOT NULL for LIVE orders

3. **Funds properly segregated**
   - PAPER trades use virtual/simulated capital
   - LIVE trades use broker account capital
   - Portfolio accounting separates PAPER and LIVE positions

## Database Verification

Query the database directly to verify execution modes:

```sql
-- View all orders with their execution modes
SELECT id, symbol, execution_mode, state, broker_order_id, created_at 
FROM oms_orders 
WHERE created_at > NOW() - INTERVAL '1 day'
ORDER BY created_at DESC 
LIMIT 20;

-- Count orders by execution mode
SELECT execution_mode, state, COUNT(*) 
FROM oms_orders 
WHERE created_at > NOW() - INTERVAL '1 day'
GROUP BY execution_mode, state;

-- View signals with linked orders
SELECT s.id, s.symbol, s.execution_mode, COUNT(o.id) as order_count
FROM strategy_signals s
LEFT JOIN oms_orders o ON s.id = o.signal_id
WHERE s.created_at > NOW() - INTERVAL '1 day'
GROUP BY s.id, s.symbol, s.execution_mode;
```

## Order State Machine

Expected state transitions for each mode:

**PAPER / SIMULATION:**
```
CREATED
  ↓
PENDING_SUBMISSION (waiting to be processed)
  ↓
ACCEPTED (execution engine accepted)
  ↓
FILLED (received fill from market data)
```

**LIVE (Eligible Trader):**
```
CREATED
  ↓
PENDING_SUBMISSION
  ↓
ACCEPTED (broker accepted)
  ↓
FILLED (broker filled)
```

**LIVE (Ineligible Trader):**
```
CREATED
  ↓
PENDING_SUBMISSION
  ↓
REJECTED or FAILED (eligibility gate triggered)
```

## Test Scenario: Multi-Mode Signal Generation

Create a test that verifies all three modes work correctly:

1. **Setup**: Have 3 user accounts:
   - User A: PAPER mode enabled
   - User B: SIMULATION mode enabled
   - User C: LIVE mode (ineligible - no broker credentials)

2. **Trigger**: Replay same strategy for all users simultaneously

3. **Verification**:
   - User A orders should FILL with PAPER fills
   - User B orders should FILL with SIMULATED fills
   - User C orders should be REJECTED due to ineligibility
   - No cross-contamination between modes

## Performance Metrics

After verification, check these performance metrics:

1. **Order Execution Latency** (PAPER mode)
   - Submission to Fill: should be < 100ms
   - Latency should be configurable (slippage simulator, market tick timing)

2. **Fill Rate** (PAPER mode)
   - Should be 100% (all PAPER orders fill)
   - Partial fills may be simulated based on order size vs available liquidity

3. **Slippage**
   - Should vary based on ATR (volatility) and order size
   - Deterministic (repeatable with same seed) for testing

## Troubleshooting

### Orders not transitioning to FILLED
- Check ExecutionSimulator logs for processing errors
- Verify market data is available for the trading date
- Check if order is in REJECTED/FAILED state instead

### LIVE orders not being rejected for ineligible traders
- Verify LiveTradingTraderEligibilityService is properly configured
- Check trader's eligibility status in admin panel
- Verify broker credentials are not set for test user

### PAPER orders showing broker order IDs
- This indicates orders are being submitted to broker (bug!)
- Check execution mode routing in ExecutionDispatcher
- Verify PaperExchangeAdapter is being used for PAPER mode

### Mixed fills (PAPER order getting LIVE fills)
- Indicates cross-contamination between execution modes
- Check order source in ExecutionSimulator
- Verify adapter selection logic in ExecutionDispatcher
